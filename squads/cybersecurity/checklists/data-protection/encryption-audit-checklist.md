# Encryption Audit Checklist

## Purpose

Checklist for auditing encryption implementations covering data at rest, data in transit, key management practices, algorithm review, and certificate management.

## Data at Rest Encryption

### Storage Encryption

| Storage Type | Encryption Required | Algorithm | Key Management | Verified |
|-------------|-------------------|-----------|---------------|----------|
| Database (production) | Yes | AES-256 | CMK in KMS/HSM | [ ] |
| Database (dev/test with prod data) | Yes | AES-256 | KMS | [ ] |
| File servers (confidential+) | Yes | AES-256 | KMS or filesystem | [ ] |
| Cloud object storage (S3/Blob/GCS) | Yes | AES-256 SSE | CMK preferred | [ ] |
| Block storage (EBS/managed disks) | Yes | AES-256 | CMK preferred | [ ] |
| Backup storage | Yes | AES-256 | Separate key from source | [ ] |
| Laptop/workstation disks | Yes | AES-256 (BitLocker/FileVault) | TPM + recovery key | [ ] |
| Mobile devices | Yes | Device-native encryption | Device passcode | [ ] |
| Removable media (if allowed) | Yes | AES-256 (BitLocker To Go) | User-managed | [ ] |
| Archive/cold storage | Yes | AES-256 | Long-term key retention | [ ] |

### Encryption Verification

- [ ] All production databases confirmed encrypted at rest
- [ ] Encryption status verified via automated scanning (not self-reported)
- [ ] Unencrypted storage instances identified and remediation tracked
- [ ] Full disk encryption enforced on all endpoints via MDM/GPO
- [ ] Full disk encryption recovery keys centrally escrowed
- [ ] Cloud storage default encryption settings enabled at account/org level
- [ ] Backup encryption independent of source system encryption
- [ ] Encryption does not rely solely on physical media encryption (e.g., SED without software encryption)

## Data in Transit Encryption

### TLS Configuration

| Service Type | Minimum TLS Version | Preferred | Verified |
|-------------|-------------------|-----------|----------|
| External web services | TLS 1.2 | TLS 1.3 | [ ] |
| Internal web services | TLS 1.2 | TLS 1.3 | [ ] |
| API endpoints | TLS 1.2 | TLS 1.3 | [ ] |
| Email (SMTP) | STARTTLS (TLS 1.2) | MTA-STS enforced | [ ] |
| Database connections | TLS 1.2 | TLS 1.3 | [ ] |
| LDAP/AD | LDAPS (TLS 1.2) | Channel binding | [ ] |
| File transfer | SFTP or FTPS | SFTP preferred | [ ] |
| VPN | TLS 1.2 or IKEv2 | IKEv2 with AES-256-GCM | [ ] |

### TLS Hardening

- [ ] TLS 1.0 and 1.1 disabled on all services
- [ ] SSL 2.0 and 3.0 disabled on all services
- [ ] Weak cipher suites disabled (RC4, DES, 3DES, MD5, NULL)
- [ ] Export cipher suites disabled
- [ ] Perfect Forward Secrecy (PFS) enabled (ECDHE preferred)
- [ ] Server cipher order enforced (server preference, not client)
- [ ] HSTS enabled on all HTTPS services (max-age >= 1 year, includeSubDomains)
- [ ] HSTS preload submitted for public-facing domains
- [ ] OCSP stapling enabled on web servers
- [ ] Certificate transparency enforced
- [ ] Compression disabled (CRIME/BREACH attack prevention)
- [ ] Renegotiation disabled or client-initiated renegotiation disabled

### Cipher Suite Recommendations

```
Preferred (TLS 1.3):
  TLS_AES_256_GCM_SHA384
  TLS_CHACHA20_POLY1305_SHA256
  TLS_AES_128_GCM_SHA256

Acceptable (TLS 1.2):
  TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
  TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256
  TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384
  TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256

Prohibited:
  Anything with RC4, DES, 3DES, MD5, NULL, EXPORT, anon
```

### Internal Network Encryption

- [ ] East-west traffic encryption assessed (service-to-service)
- [ ] Service mesh with mTLS deployed for microservices (if applicable)
- [ ] Database connections use TLS (not cleartext)
- [ ] LDAP uses LDAPS or STARTTLS (not cleartext LDAP)
- [ ] SNMP v3 used with encryption (v1/v2c eliminated)
- [ ] Syslog uses TLS (not UDP/TCP cleartext)
- [ ] Internal APIs use TLS
- [ ] Management protocols use encrypted channels (SSH not Telnet)

## Key Management

### Key Lifecycle

| Phase | Requirement | Verified |
|-------|------------|----------|
| Generation | Keys generated by FIPS 140-2 Level 2+ validated module (or KMS) | [ ] |
| Storage | Keys stored in KMS/HSM, not in application code or config files | [ ] |
| Distribution | Keys distributed via secure channel (KMS API, not email) | [ ] |
| Usage | Keys used only for intended purpose (encryption, signing, not both) | [ ] |
| Rotation | Automatic rotation configured per policy | [ ] |
| Archival | Retired keys archived for decryption of historical data | [ ] |
| Destruction | Destroyed keys cannot be recovered, destruction documented | [ ] |

### Key Rotation Schedule

| Key Type | Rotation Period | Method | Verified |
|----------|----------------|--------|----------|
| KMS master keys | Annual | Automatic (cloud KMS) | [ ] |
| Data encryption keys | Per-object or daily | Envelope encryption | [ ] |
| TLS certificates | 90 days (public), 1 year (internal) | Automated renewal | [ ] |
| SSH keys | 90 days | Certificate-based preferred | [ ] |
| Code signing keys | Annual | Manual with ceremony | [ ] |
| Backup encryption keys | Annual | Manual with dual custody | [ ] |

### Key Management Controls

- [ ] Key access restricted to minimum necessary personnel/services
- [ ] Key access logged and auditable
- [ ] Key usage logged (encryption/decryption operations)
- [ ] Separation of duties: key administrators cannot access encrypted data
- [ ] Key backup/escrow procedures documented
- [ ] Key recovery procedure tested
- [ ] No hard-coded keys in source code (verified by scanning)
- [ ] Key material never transmitted in cleartext
- [ ] Multi-party key ceremonies for root/master keys documented

## Algorithm Review

### Current Algorithm Assessment

| Algorithm | Status | Action Required |
|-----------|--------|----------------|
| AES-256-GCM | Approved | None |
| AES-128-GCM | Approved | Prefer AES-256 for new deployments |
| RSA 2048+ | Approved | Plan migration to 3072+ or ECDSA |
| RSA 1024 | Deprecated | Immediate replacement |
| ECDSA P-256+ | Approved | Preferred for new deployments |
| SHA-256+ | Approved | None |
| SHA-1 | Deprecated | Replace in all uses |
| MD5 | Prohibited | Immediate replacement |
| 3DES | Deprecated | Replace within 6 months |
| DES | Prohibited | Immediate replacement |
| RC4 | Prohibited | Immediate replacement |
| Blowfish | Deprecated | Replace with AES |

### Post-Quantum Readiness

- [ ] Crypto inventory completed (all algorithms in use cataloged)
- [ ] Dependency on vulnerable algorithms identified (RSA, ECDSA, DH)
- [ ] Migration timeline to post-quantum algorithms planned
- [ ] Hybrid approaches evaluated (classical + PQC)
- [ ] Vendor PQC roadmaps reviewed
- [ ] NIST PQC standard candidates tracked (ML-KEM, ML-DSA)

## Certificate Management

### Certificate Inventory

- [ ] All certificates inventoried (internal and external)
- [ ] Certificate expiration monitoring configured
- [ ] Alert on certificates expiring within 30 days
- [ ] Critical alert on certificates expiring within 7 days
- [ ] Expired certificates identified and replaced
- [ ] Certificate authority (CA) hierarchy documented
- [ ] Root CA certificates secured (offline or HSM)

### Certificate Operations

- [ ] Automated certificate renewal deployed (ACME/Let's Encrypt or internal CA)
- [ ] Certificate provisioning workflow documented
- [ ] Certificate revocation procedure documented and tested
- [ ] CRL/OCSP infrastructure operational and monitored
- [ ] Certificate transparency logs monitored for unauthorized issuance
- [ ] Wildcard certificate usage minimized and justified
- [ ] Certificate key size meets minimum requirements (RSA 2048+, ECDSA P-256+)
- [ ] Private keys stored securely (HSM for CA, TPM for servers where possible)
